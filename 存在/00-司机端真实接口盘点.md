# 司机端模块真实接口盘点

> 基于代码实际定义整理（api/driver/driver.api、rpc/driversvc/proto/driversvc.proto、各 logic 实现）。
> 只记录已实现内容，未实现/未核实的标 TODO，禁止当已实现写进答辩。

## 1. 模块边界（我负责的部分）

- `api/driver`：司机端 HTTP 网关（go-zero api），做鉴权、参数校验、聚合调用下游 RPC。
- `rpc/driversvc`：司机微服务（go-zero rpc），负责司机账号、在线状态、车辆、资质、AI 推荐分。

不属于我、仅做对接的服务（不修改其代码）：
- `ordersvc`：订单服务，接单/行程/完单状态机在它那里。
- `dispatchsvc`：派单服务，派单记录列表来自它。
- Redis：在线状态权威存储（TTL 60s 保活）。

## 4. 关键实现事实（写实）

### 4.1 在线状态以 Redis 为权威
- `onlinestore` 包：key=`driver:online:{driverID}`，Hash 存 online_status/device_id/经纬度，TTL 默认 60s。
- 心跳续期 TTL 保活；超 TTL 视为离线。
- MySQL `driver_location` 仅做持久化兜底与派单查询，不是权威源。
- 多端互踢：心跳比对 `device_id`，不一致返回 `kicked=true`，客户端强制重登。

### 4.2 AI 推荐分是加权公式，不是大模型
- 权重：服务分 0.45 + 取消率 0.25 + 投诉 0.15 + 当月完单 0.15。
- 各维度归一化到 [0,1] 后加权求和得 0~100 分。
- 降级：查不到服务分或异常 → `degraded=true`，回退"距离优先"，不阻断打车链路。
- 注意：叫"AI 推荐分"但实际是规则加权，没有训练模型/大模型推理。

### 4.3 接单/行程不在 driversvc 内
- accept/start-trip/confirm-arrive/finish-trip 由 api/driver 直接调 ordersvc。
- 行程开始/结束顺带调 driversvc.SetDriverServiceStatus 切换 1(在线)/2(行程中)。
- 司机端不持有订单状态机。

### 4.4 派单列表是聚合接口
- `ListMyDispatches`：调 dispatchsvc.ListDispatchRecords（按 driver_id 分页），逐条调 ordersvc.GetOrder 拼装摘要。
- 分页 page/pageSize/status，前端约定每页 10。

### 4.5 我的订单列表来自 ordersvc
- `ListMyOrders`：api/driver 从 JWT 获取当前司机 ID，转发到 ordersvc.ListOrders(driver_id)。
- status=0 表示全部订单，1-6 对应订单状态枚举。
