# 司机端模块 三性六讲

## 三性

### 1. 完备性
- 司机端主链路接口齐全：注册/登录（密码+短信）、上线/心跳/下线/位置上报、接单/拒单/开始行程/确认到达/完单、派单列表分页、资质上传查询、AI 推荐分查询，覆盖了司机从入驻到完单的核心场景。
- 跨服务对接完整：网关层把 driversvc / ordersvc / dispatchsvc 三块能力串起来，司机端一个入口能跑通业务。
- 不完备的地方（写实）：AgentChat 接口挂了路由但实现未核实，没写进答辩范畴；短信验证码的存储与校验位置不在本模块核实范围内。

### 2. 一致性
- 状态语义一致：online_status 在 driversvc proto、onlinestore、MySQL driver_location 三处都用 0离线/1在线/2行程中，没有各写各的。
- 接口契约一致：api/driver 的 types 与 driversvc/ordersvc/dispatchsvc 的 proto message 字段一一对应，网关只做透传与拼装，不擅自改字段含义。
- 命名一致：Redis key 统一 `driver:online:{id}`，TTL 统一 60s，心跳和上线都走同一套 Store 方法。

### 3. 健壮性
- 参数校验：driverID<=0、orderID<=0、deviceID 空、经纬度非法都有显式拦截，返回明确业务错误。
- 降级不中断：AI 推荐分查不到服务分记录时 `degraded=true` 回退距离优先，不抛错断链。
- 客户端缺失保护：orderClient/driverClient/dispatchClient 取用时判空，未配置返回 ErrClientNotConfigured，避免空指针。
- 已知不足：Redis 与 MySQL 有短暂不一致窗口（TTL 内以 Redis 为准），未做强一致补偿；心跳失败直接返回 err，没有本地重试。

## 六讲

### 1. 讲背景
实训项目 XiaoLong-Ridy 网约车，整体 go-zero 微服务。我分到的模块是司机端：一个 HTTP 网关 `api/driver` 做聚合，背后一个 `rpc/driversvc` 做司机自己的数据和服务。订单、派单是别人的服务，我只调用不改动。我 Go 有一点基础，go-zero 是第一次实战，很多高级方案（比如用 kafka 做事件总线、用分布式锁做派单）知道但自己没落地，优先选能跑起来的简单方案。

### 2. 讲需求
司机端要支撑司机从入驻到赚钱的全过程：
- 入驻：注册/登录、上传身份证驾驶证行驶证资质。
- 听单：上线、心跳保活、位置上报，让派单引擎能找到在线司机。
- 接单：收到派单列表、接单或拒单、开始行程、确认到达、完单上报里程时长金额。
- 辅助：查自己的 AI 推荐分，看哪些指标拖后腿。

### 3. 讲设计
- 网关聚合：api/driver 不存业务状态，只做鉴权（JWT 解析 driverID）+ 参数校验 + 调下游 RPC。
- 在线状态用 Redis 当权威：司机上线写 Hash 并设 60s TTL，心跳续期；MySQL 只兜底。好处是心跳高频读写不压 MySQL，派单引擎查附近司机也走 Redis 快。
- 多端互踢放心跳里做：比对 device_id，新设备登录顶掉旧设备，心跳返回 kicked 让旧端重登。
- AI 推荐分用规则加权：四个维度归一化加权，没上模型，原因是我搞不定模型训练和特征工程，且规则可解释、好调试。

### 4. 讲实现
- go-zero api 用 .api 文件定义路由和结构体，goctl 生成 handler/logic 骨架，我在 logic 里填业务。
- driversvc 的 online 状态抽出一个 `onlinestore` 包专门管 Redis 读写和互踢判定，logic 只调它，职责清晰。
- 接单链路：api/driver 的 OrderLogic 直接调 ordersvc 的 AcceptOrder/StartTrip 等，行程开始调 driversvc.SetDriverServiceStatus(2)，结束调回(1)，自身状态跟着订单走。
- 派单列表：ListMyDispatches 先查 dispatchsvc 拿记录，再逐条查 ordersvc 拼订单摘要，分页参数透传。

### 5. 讲难点踩坑
- 踩坑1：go-zero 的 api 生成代码和 rpc 客户端注入。一开始不知道 svc.ServiceContext 里怎么挂多个 RPC client，是照着生成的 svc 结构体一个个加字段、在 etc 配 yaml 的 Endpoints 才跑通。
- 踩坑2：在线状态到底以谁为准。最早想直接写 MySQL，但心跳频率高会压库，也慢；改成 Redis 权威后，又遇到 Redis 挂了司机全"离线"的问题，最后用 MySQL 兜底 + 降级处理。
- 踩坑3：多端互踢。一开始只在"上线"时判断设备，结果旧手机没退出也能接单。后来把互踢判定挪到每次心跳比对 device_id 才解决。
- 踩坑4：派单列表 N+1 查询。先查 dispatchsvc 拿到列表，再循环查 ordersvc，列表长时RT高。受限于能力和时间，先用分页（每页10）压住，没上批量查询或缓存。
- 踩坑5：AI 推荐分被名字误导。答辩时差点说成"用了大模型"，实际是加权公式，后来在文档里老实写清楚是规则计算+降级。

### 6. 讲优化与不足
- 不足1（N+1）：派单列表逐条查订单，应改 ordersvc 提供批量 GetOrders 或 dispatchsvc 直接带订单快照。受限于跨服务改动边界，未做。
- 不足2（一致性）：Redis 和 MySQL 最终一致，极端情况派单引擎读到旧位置。可加位置变更事件，但没上 kafka。
- 不足3（重试）：心跳失败直接报错，客户端无退避重试，弱网会误离线。
- 优化点（已做）：AI 分降级保证链路不中断；客户端判空避免空指针；参数校验前置减少无效 RPC。
- 可改进（未来）：派单用 kafka 事件驱动、在线状态加分布式锁、AI 分接真实模型——这些我知道但实训阶段没落地。
