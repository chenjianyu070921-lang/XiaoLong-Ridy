# 司机端模块 功能亮点

> 客观写实，区分"已实现"和"受能力限制未完全落地"。不写没做过的大模型能力。

## 已实现（真实跑通）

1. **司机全生命周期入口**：注册/密码登录/短信登录、资质上传与查询、上线/心跳/下线/位置上报，一条龙打通，司机从入驻到听单无需切多个服务。
2. **Redis 权威的在线状态 + 心跳保活**：TTL 60s 续期，高频心跳不压 MySQL；MySQL 仅兜底，派单引擎查附近司机走 Redis 快。
3. **多端互踢**：心跳比对 device_id，新设备顶掉旧设备并返回 kicked，避免一个司机多端同时接单的脏数据。
4. **接单到完单闭环**：接单/拒单/开始行程/确认到达/完单，网关聚合 ordersvc 与 driversvc，行程中自动切"行程中"状态，完单切回"在线"。
5. **派单列表分页聚合**：组合 dispatchsvc 派单记录 + ordersvc 订单摘要，分页每页 10 条，司机端一眼看到待接派单。

## 受能力限制未完全落地（如实写）

1. **AI 推荐分是规则加权，非大模型**：服务分/取消率/投诉/完单四维度加权得 0~100 分，名字带"AI"但实际是公式，没做模型训练。已做降级（查不到服务分回退距离优先）。
2. **派单列表 N+1 查询未优化**：逐条查 ordersvc，列表长时 RT 偏高。受跨服务边界限制，先用分页压住，没上批量接口或缓存。
3. **强一致与事件驱动未做**：Redis/MySQL 有短暂不一致窗口；位置变更没走 kafka 事件。知道该做，但实训阶段未落地。
4. **心跳无客户端重试**：心跳失败直接报错，弱网下可能误判离线，没做退避重试。
5. **AgentChat 接口挂了路由但未核实实现**：不写入"已实现"范畴，避免答辩吹牛。
