# XiaoLong-Ridy 网约车 · 司机端模块 实训答辩文档

> 适用场景：实训答辩，可直接复制到 Word。全文基于已实现代码写实，未虚构功能。

## 一、自我介绍

你好，我是本项目司机端模块的开发者。我有一定的 Go 基础，但 go-zero 是第一次实战。项目里我负责司机端：一个 HTTP 网关 `api/driver` 做聚合，背后一个 `rpc/driversvc` 做司机自己的数据和服务。订单和派单是同学负责的模块，我只调用不改动。我选方案时优先"能跑起来、好调试"，很多高级架构（kafka 事件总线、分布式锁派单）我知道但实训阶段没落地，文档里会如实区分。

## 二、项目介绍

XiaoLong-Ridy 是一个网约车平台，整体 go-zero 微服务架构，按领域拆成多个服务。我负责的司机端要支撑司机从入驻到赚钱的全过程：

- **入驻**：注册/登录（密码+短信）、上传身份证/驾驶证/行驶证资质。
- **听单**：上线、心跳保活、位置上报，让派单引擎能找到在线司机。
- **接单**：收到派单列表、接单或拒单、开始行程、确认到达、完单上报里程时长金额。
- **辅助**：查自己的 AI 推荐分，看哪些指标拖后腿。

技术形态：`api/driver`（go-zero api，HTTP JSON）对外，内部通过 gRPC 调 `driversvc`；在线状态走 Redis；接单/行程调 `ordersvc`；派单列表调 `dispatchsvc`。

## 三、三性

### 1. 完备性
司机端主链路接口齐全：注册/登录、上线/心跳/下线/位置上报、接单/拒单/开始行程/确认到达/完单、派单列表分页、我的订单列表分页、资质上传查询、AI 推荐分查询，覆盖入驻到完单核心场景。跨服务对接完整，一个入口跑通业务。不完备：AgentChat 接口挂了路由但实现未核实，未写进答辩；短信验证码存储校验不在本模块核实范围。

### 2. 一致性
- 状态语义一致：online_status 在 proto、onlinestore、MySQL 三处都用 0离线/1在线/2行程中。
- 接口契约一致：api/driver 的 types 与下游 proto message 字段一一对应，网关只透传与拼装。
- 命名一致：Redis key 统一 `driver:online:{id}`，TTL 统一 60s。

### 3. 健壮性
- 参数校验：driverID/orderID 非法、deviceID 空、经纬度非法都有拦截。
- 降级不中断：AI 推荐分查不到服务分记录时 `degraded=true` 回退距离优先。
- 客户端缺失保护：RPC client 取用判空，避免空指针。
- 不足：Redis 与 MySQL 有短暂不一致窗口；心跳失败无客户端重试。

## 四、六讲

### 1. 讲背景
实训项目，我分到司机端。go-zero 第一次实战，优先简单可落地方案。订单、派单是别人的服务，我只调用。

### 2. 讲需求
司机从入驻到完单：注册登录、资质、听单（上线/心跳/位置）、接单拒单、行程、完单、查推荐分。

### 3. 讲设计
- 网关聚合：api/driver 只做鉴权（JWT 解析 driverID）+ 校验 + 调下游。
- 在线状态 Redis 权威：上线写 Hash 设 60s TTL，心跳续期；MySQL 兜底。好处是心跳高频不压库，派单查附近走 Redis 快。
- 多端互踢放心跳：比对 device_id，新设备顶旧设备返回 kicked。
- AI 推荐分规则加权：四维度归一化加权，可解释好调试，没上模型。

### 4. 讲实现
- goctl 生成 api/rpc 骨架，logic 填业务。
- onlinestore 包专管 Redis 读写和互踢，logic 只调它。
- 接单链路：OrderLogic 调 ordersvc，行程开始调 driversvc.SetDriverServiceStatus(2)，结束调回(1)。
- 派单列表：先查 dispatchsvc，逐条查 ordersvc 拼摘要，分页透传。
- 我的订单列表：按 JWT 中的司机 ID 调 ordersvc.ListOrders，不信任客户端传 driverId。

### 5. 讲难点踩坑
- 踩坑1：svc.ServiceContext 挂多个 RPC client，照生成结构加字段、配 yaml Endpoints 才跑通。
- 踩坑2：在线状态以谁为准——改 Redis 权威后遇 Redis 挂全离线，用 MySQL 兜底+降级。
- 踩坑3：多端互踢最初只在上线判断，旧手机能接单；挪到心跳比对 device_id 才解决。
- 踩坑4：派单列表 N+1 查询，逐条查 ordersvc，RT 高；先用分页压住，没上批量。
- 踩坑5：AI 推荐分差点说成大模型，实际是加权公式，文档如实写。

### 6. 讲优化与不足
- N+1 未优化（受跨服务边界限制）。
- Redis/MySQL 最终一致，极端读到旧位置；位置变更没走 kafka。
- 心跳无客户端退避重试。
- 可改进：派单 kafka 事件驱动、在线状态分布式锁、AI 分接真实模型——知道但未落地。

## 五、功能亮点

1. **司机全生命周期入口**：注册/登录/资质/上线/心跳/接单/完单一条龙。
2. **Redis 权威在线状态 + 心跳保活**：高频心跳不压 MySQL，派单查附近走 Redis。
3. **多端互踢**：心跳比对 device_id，避免一司机多端接单脏数据。
4. **接单到完单闭环**：网关聚合 ordersvc 与 driversvc，行程中自动切"行程中"。
5. **派单列表分页聚合**：dispatchsvc + ordersvc 组合，每页 10 条。

## 六、难点总结（答辩口述版）

- 服务拆分下的网关聚合：搞清谁的状态机在哪儿（订单在 ordersvc，在线在 driversvc）。
- 在线状态的存储选型：Redis 权威 vs MySQL，权衡性能与一致性。
- 多端互踢的时机：上线判断不够，必须心跳持续校验。
- 跨服务调用的边界感：只对接不改动他人代码，用分页和聚合接口兜底能力限制。

## 七、优化与可改进点（答辩收尾）

- 短期：派单列表改批量查询或缓存，降 N+1 RT；心跳加客户端退避重试。
- 中期：位置变更发 kafka 事件，派单引擎实时消费，去掉 Redis/MySQL 不一致窗口。
- 长期：AI 推荐分从规则加权演进到真实模型；在线状态引入分布式锁防并发写。

## 八、诚实声明（防答辩被问死）

- AI 推荐分 = 规则加权公式，**不是大模型**，名字带 AI 只是业务叫法。
- AgentChat 接口存在但实现未核实，不在已实现范畴。
- kafka 在本模块未实际使用，仅在架构图作为"未来演进"标注。
