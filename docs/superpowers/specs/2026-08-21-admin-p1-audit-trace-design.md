# 管理后台 P1 数据完整性设计

## 目标

补齐优惠券实际发放的发布追溯记录，以及登录、下单两个真实业务入口的黑名单命中记录。管理后台只查询命中记录，不承担跨服务伪造写入。

## 优惠券发布记录

`admin_coupon_publish_record` 仅记录具有 `coupon_id` 的优惠券实际发放行为。`IssueCoupon` 在同一数据库事务中创建发券任务、写入用户券和更新统计后，写入一条发布记录：发布版本使用任务号，发布范围使用 `full`，目标配置复用发券请求配置，状态按发放结果写入成功、部分失败或失败，记录操作管理员。

`promotion_activity` 没有 `coupon_id`，活动发布和回滚继续由活动表与操作日志审计，不写入优惠券发布记录，避免形成错误关联。

## 黑名单命中记录

`usersvc.LoginBySMS` 与 `ordersvc.CreateOrder` 在各自业务入口检查 `blacklist` 表。当前基础表的 `target_id` 为数值字段，且目标类型定义为 `user/driver/device`，因此登录在用户定位完成后与下单一致，均按 `user` 加用户 ID 检查；不将手机号错误映射为数值 ID。命中后向 `risk_blacklist_hit_record` 写入 `login` 或 `order` 场景、目标、关联黑名单 ID、风险等级、原因与请求链路 ID。

首轮只记录命中，不改变当前登录或下单的准入结果，避免未经产品确认的业务拦截。检查失败不影响原业务，但应记录错误日志；命中记录写入失败返回错误，避免成功业务动作不可追溯。

## 数据一致性

优惠券发放和发布记录使用同一事务。登录、下单服务的黑名单检查与命中记录使用其本地数据库连接；不由 adminsvc 直接写其他服务的业务入口记录。

## 验证

- 发券成功、部分失败、失败均有对应发布记录，事务失败不残留记录。
- 登录手机号黑名单、下单用户黑名单命中时写入正确场景记录。
- 未命中不写记录；检查失败的降级行为与写入失败的失败返回均有测试。
