# 管理后台 P1/P2 闭环整改设计

日期：2026-08-31

## 一、目标与范围

本次整改用于解决管理后台“后端接口已存在、前端页面不可用或能力不可验收”的问题，范围限定在现有模块三边界内：

- `web/admin`：为已开放的后台接口提供可操作的页面、筛选、详情、状态展示和错误重试。
- `api/admin`：仅在前端需要且当前路由缺失时补充 HTTP 入口，保持现有 `/admin/v1` 契约。
- `rpc/adminsvc`：完善统计、风控、工单、通知补偿和订单操作的可追踪行为。
- `job`：验证并补充已有 `admin_audit_outbox` 通知/审计补偿执行链路。
- `scripts/admin-test`：补充跨服务联调前置检查和只读/错误路径验证。
- `docs/admin`：删除联调文档中的孤立误改内容，并补充当前验证结论。

本次不创建 `reportsvc`、`punishsvc`、`auditsvc`、`workordersvc`、`couponsvc`，不修改数据库表结构、迁移脚本和共享业务数据，不重写其他模块的业务逻辑。

## 二、功能设计

### 2.1 前端页面与接口一致性

保留现有 Vue 3、Element Plus、Pinia、Hash 路由和 API 封装方式。将当前大量复用 `console/index.vue` 的菜单按业务域补齐为可用页面或明确的业务面板：

- 统计：展示总览、订单、司机、财务、用户、优惠券指标，支持时间范围、刷新、加载态、空态和错误重试。
- 风控：黑名单列表、新增、解除；风险命中列表、处置动作、处置状态和局部刷新。
- 工单：列表、详情、创建、分配、跟进、仲裁、结案、重开、批量处理和证据列表。
- 导出：任务列表、任务详情、状态轮询、成功后下载、失败提示。
- 营销：优惠券、发券任务、计价规则、活动配置使用真实表单和真实操作入口。
- 订单：列表、异常订单、详情中的取消、轨迹、改派和退款操作使用统一状态判断和操作反馈。

所有页面只调用 `src/api`，不直接拼接底层请求。请求体严格匹配 `api/admin/internal/types`，金额使用字符串或整数分单位，JSON 配置在提交前校验。写操作统一二次确认、提交中禁用、成功后重新加载详情或列表。

### 2.2 统计、风控、工单和通知闭环

- 统计继续使用 `adminsvc` 实时聚合，不引入报表服务；前端展示查询时间范围和数据更新时间，并对不支持的 `city_code` 返回明确错误。
- 风控命中处置沿用现有 `review_pass`、`add_blacklist`、`create_work_order` 三类动作；页面展示派生的处置状态、关联工单或黑名单，重复处置显示冲突原因。
- 工单沿用现有状态机和乐观锁版本号；前端根据后端返回的允许动作展示按钮，版本冲突后重新加载详情。
- 司机冻结、司机风控拉黑和审核动作的通知继续通过 `pushsvc`；通知失败必须记录 `admin_audit_outbox`，由 `job` 重试。页面区分“业务动作成功”和“通知补偿中”，不能把通知失败伪装成全部成功。
- 对于通知链路尚未启动的环境，后台接口保留业务结果，返回或记录可追踪的补偿信息，不生成虚假通知成功记录。

### 2.3 订单跨服务联调

订单取消、退款、改派统一通过：

```text
web/admin -> api/admin -> adminsvc -> ordersvc
```

`adminsvc` 负责管理员鉴权、幂等号、审计和错误映射，`ordersvc` 负责订单状态机、金额边界、司机释放/重新派单及退款事件。联调脚本不使用 dummy ordersvc 作为成功依据；若真实 `ordersvc` 因配置冲突无法启动，脚本必须明确标记为阻塞并停止声称闭环通过。

联调覆盖：

- 可取消订单成功、非法状态拒绝、重复 request_id 幂等。
- 退款金额边界、重复退款、订单状态更新和退款事件发布。
- 改派目标司机校验、原派单释放、目标司机绑定和重复 request_id 幂等。
- 订单详情刷新能够看到操作后的状态和关联流水。

测试只使用明确的测试数据和环境变量，不执行迁移，不对未知生产数据执行写操作。

### 2.4 联调文档修复

`docs/admin/管理后台订单与司机审核当日联调记录.md` 当前 `order_no` 表格行后存在孤立的 `7`。该内容不属于字段定义或验收结果，判定为误改并删除；保留其余用户已有修改，不做重排或历史内容清理。

## 三、错误处理与安全边界

- 未登录统一清理前端会话并跳转登录页。
- 400、404、409、410、403 和 500 分别显示参数、资源、状态冲突、资源过期、权限和系统错误。
- 业务操作成功但通知/审计补偿失败时，页面显示“业务已完成，补偿待处理”，并允许刷新查看。
- 前端不显示 MySQL DSN、Redis 密码、服务器绝对文件路径或内部异常堆栈。
- 不信任前端角色决定后端权限，所有写操作继续由 adminsvc 服务端 RBAC 校验。

## 四、验证方案

1. 运行 `go test ./...`，确认所有 Go 模块回归通过。
2. 运行管理后台专项测试，覆盖无 token、参数错误、资源不存在、状态冲突和幂等错误。
3. 使用本地 Node/Vite 入口运行 `web/admin`，执行构建；若环境工具链失败，记录为环境阻塞而非代码通过。
4. 启动真实 `ordersvc`、`driversvc`、`adminsvc`、`api/admin`，执行订单取消、退款、改派联调；禁止用 dummy 服务替代成功结论。
5. 验证后台前端各菜单均能进入对应页面，页面请求路径与后端路由一一对应。
6. 检查 `git diff`，确认不修改数据库结构、业务数据和无关模块。

## 五、验收标准

- 所有当前开放的后台接口均有页面入口、详情入口或明确的任务面板。
- 统计、风控、工单和通知补偿能够从页面发起、看到结果并追踪失败。
- 订单取消、退款、改派只有在真实下游服务成功时才标记为联调通过。
- 联调文档不再包含孤立 `7`，且既有其他修改保持不变。
- Go 测试通过；前端构建或环境阻塞状态有明确证据。
