# 管理后台凭据与 RBAC 安全设计

## 目标

消除管理后台配置中的 MySQL 明文凭据，并在 `adminsvc` 服务端落实最小角色权限控制。HTTP 网关只负责解析并透传已验证会话的操作者信息；敏感操作最终必须由 `adminsvc` 校验身份和权限。

本设计不修改数据库结构、不写入业务数据，也不改变既有后台接口路径和成功响应结构。

## 凭据配置

`api/admin/etc/admin.json` 和 `rpc/adminsvc/etc/admin.yaml` 不再保存真实 MySQL DSN，只保留空值或示例占位说明。

服务启动时按以下优先级读取 DSN：

1. `api/admin`：`ADMIN_API_MYSQL_DSN`。
2. `rpc/adminsvc`：`ADMINSVC_MYSQL_DSN`。
3. 未设置环境变量时，保留配置文件 DSN 作为本地兼容回退；配置值为空则启动失败，并提示需要设置对应环境变量。

真实共享库密码必须由负责人在数据库侧轮换。轮换后的 DSN 只存放在本机环境变量、CI Secret 或部署平台 Secret 中，不能重新提交到仓库。

## 授权数据流

1. HTTP 中间件调用 `adminsvc.ValidateSession`，得到管理员 ID、角色和账号状态。
2. HTTP 中间件将已验证 token 写入 gRPC metadata；写请求继续携带原有管理员 ID 供审计。
3. `adminsvc` 在每个写操作及受限读操作的入口调用统一授权函数。
4. 授权函数校验：管理员 ID 大于零、角色合法、请求声明角色与服务端会话角色一致；不满足权限矩阵时返回 `codes.PermissionDenied`。
5. HTTP 层将 `codes.PermissionDenied` 映射为 HTTP 403 和业务码 `40003`。

为避免 RPC 客户端伪造身份，管理员角色不能只信任请求参数。服务端必须根据 token 回查 Redis 会话和 `admin_user` 的角色、状态，并校验写请求中的 `admin_id` 与会话管理员 ID 一致。

## RPC 契约

不扩展现有 protobuf 请求字段，避免无意义的契约膨胀。token 通过 `x-admin-token` gRPC metadata 透传；服务端拦截器统一校验。`Register` 作为例外方法，在已有管理员时仍从 metadata 回查 `operator_admin_id` 的真实角色，不能信任客户端传入的 `operator_role`。

## 测试与验收

1. 配置加载测试：环境变量覆盖配置；两者均为空时返回明确错误。
2. RPC 授权测试：客服执行冻结、发券、改价、加黑名单均返回 `PermissionDenied`；运营执行改价、黑名单、发券停用返回 `PermissionDenied`；超管允许。
3. 身份一致性测试：不存在、停用的管理员 ID，或请求角色与数据库角色不一致时拒绝。
4. HTTP 回归：权限拒绝统一返回 `403/40003`，正常角色保留原有成功行为。
5. 执行 `go test ./api/admin/... ./rpc/adminsvc/...`，使用项目内独立 `GOCACHE`，避免系统目录权限干扰。

## 非目标

- 不新增角色、权限表或按钮级权限管理。
- 不实现 mTLS、网关签名或完整服务网格身份认证；该项作为后续服务间零信任改造。
- 不修改价格、订单、优惠券等业务规则。
