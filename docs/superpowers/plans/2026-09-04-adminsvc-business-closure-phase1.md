# adminsvc 第一阶段业务闭环实施计划

> 对应设计：[2026-09-04-adminsvc-business-closure-phase1-design.md](../specs/2026-09-04-adminsvc-business-closure-phase1-design.md)

## 实施原则

1. 仅在现有 `api/admin`、`rpc/adminsvc`、`job`、`mq-consumer` 和已有下游服务边界内扩展；
2. 新增数据库对象只通过迁移脚本交付，不自动执行；
3. 每个写操作在同一事务内落业务状态、审计日志和 `admin_domain_outbox`；
4. 所有下游事件必须有事件号、业务幂等号、最大重试次数和失败状态；
5. 每个阶段先补测试，再实现逻辑，再执行受影响包测试。

## 阶段 0：基线与公共能力

### 0.1 文档和迁移

- 新增 `scripts/sql/migrate/` 中的第一期后台业务迁移脚本。
- 创建处罚规则、处罚单、处罚申诉、退款补偿、发券批次、活动发布任务和领域 outbox 表。
- 为任务状态、聚合幂等键、下次重试时间、司机 ID、订单 ID、批次号建立索引。
- 迁移脚本只包含 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX` 和必要约束。

### 0.2 adminsvc 公共组件

- 在 `rpc/adminsvc/internal/logic/adminservice` 新增领域任务与 outbox 公共 helper。
- 定义统一事件信封和事件类型常量。
- 实现 outbox 状态迁移、租约抢占、指数退避、最大重试次数、幂等查询。
- 复用现有 `admin_operation_log` 与 `admin_audit_outbox`，不破坏其兼容语义。

### 0.3 测试

- SQL mock 测试：业务数据、审计日志、领域 outbox 同事务提交。
- 状态机测试：非法状态跳转、重复 request_id、并发条件更新。
- 事件序列化测试：禁止包含密码、token 和明文身份信息。

## 阶段 1：司机处罚与申诉

### 1.1 RPC 和 HTTP 契约

- 扩展 `rpc/adminsvc/admin.proto`，新增处罚规则、处罚单、处罚申诉的 DTO 与 RPC。
- 更新生成代码并在 `api/admin/internal/types` 增加 HTTP 请求/响应结构。
- 在 `api/admin/internal/handler` 注册处罚规则、处罚单和申诉路由。
- 在前端 `web/admin/src/api/modules.js` 增加处罚模块 API，并新增专属页面入口。

### 1.2 业务逻辑

- 处罚规则创建、修改、启停和版本校验。
- 创建处罚单：校验司机、订单关联、动作组合、罚款金额和 `request_id`。
- 处罚单创建后写操作日志与 `admin.driver.punishment.requested` outbox。
- 处罚撤销和申诉审核生成反向事件，禁止直接改 `driversvc` 表。
- 罚款只生成待结算记录，不写司机余额。
- 角色：超管全权限；运营可创建处罚和初审申诉；客服只读。

### 1.3 下游执行

- `driversvc` 新增仅接受后台可信事件的处罚执行入口或 Kafka 消费逻辑。
- 司机动作按事件号和处罚单号幂等执行。
- 执行结果发布或回写，更新 `admin_driver_punishment` 为 `effective`、`failed` 或可重试状态。

### 1.4 测试

- 处罚状态机、权限、规则停用、重复处罚、撤销和申诉并发复核。
- `driversvc` 对冻结、禁接单、扣分、降权的幂等执行测试。
- API 路由、参数和错误码测试。

## 阶段 2：退款补偿

### 2.1 adminsvc 任务化

- 保留现有退款入口和订单服务状态机。
- 退款失败、超时或通道不可用时创建 `admin_refund_compensation_task` 与 `admin.refund.compensation.requested` outbox。
- 使用 `refund_no`、订单 ID 和 `request_id` 防止重复创建。
- 定义 `pending`、`processing`、`retrying`、`success`、`manual_review`、`failed` 状态转移。

### 2.2 paysvc / ordersvc 协作

- 明确订单服务退款事件与支付服务补偿事件的契约。
- `paysvc` 按退款单号幂等调用支付通道。
- 返回成功、明确业务拒绝、可重试失败三类结果。
- 最大次数后切换人工处理，不重复自动发起资金动作。

### 2.3 测试

- 原支付金额边界、重复退款、同退款单重复补偿。
- 超时与业务拒绝差异、重试退避和人工处理。
- 订单、支付、adminsvc 三方失败场景。

## 阶段 3：活动冲突检测与发布下发

### 3.1 pricesvc 能力

- 定义真实冲突检测 RPC：按城市、时间、人群、活动类型、优惠规则和优先级返回冲突列表。
- 定义按版本发布、回滚活动规则 RPC 或消费者接口。
- 确保相同活动版本重复下发不重复生效。

### 3.2 adminsvc 编排

- 发布前校验活动配置并调用 `pricesvc` 冲突检测。
- 创建 `admin_promotion_publish_task`、审计日志和发布/回滚 outbox。
- 下游失败时保留任务并重试；业务冲突直接返回冲突明细。
- 回滚创建独立反向任务，不覆盖历史版本。

### 3.3 测试

- 时间重叠、城市重叠、用户人群重叠、规则冲突、灰度冲突。
- 发布成功、重复发布、下游超时、回滚和版本乱序。

## 阶段 4：大批量异步发券

### 4.1 批次与分片

- 将现有同步发券改造为创建 `admin_coupon_issue_batch`。
- 保存目标配置、总数、成功数、失败数、分片游标、状态和 request_id。
- 创建 `admin.coupon.issue.requested` outbox。
- `job` 或专用消费者按可配置批次大小分片投递。

### 4.2 usersvc 执行

- `usersvc` 新增后台批量发券事件消费。
- 每个用户按 `batch_no + coupon_id + user_id` 幂等。
- 对无效用户、已达上限、重复请求返回可归类失败原因。
- 每分片回写批次统计和处理位置。

### 4.3 测试

- 大批次分片、部分成功、重复用户、领取上限、失败恢复。
- worker 崩溃后从游标恢复。
- 批次取消、重复消息和状态回写竞争。

## 阶段 5：可靠投递与任务运行

### 5.1 job

- 在 `job/internal/task` 新增领域 outbox 任务。
- 使用条件更新实现租约抢占，避免多实例重复处理。
- 根据事件类型投递 Kafka，并处理回调或消费结果。
- 实现指数退避、失败告警数据和死信/人工处理状态。

### 5.2 Kafka 和消费者

- 为第一期事件新增 topic、键规则、消费者组和配置项。
- 消费者确认成功后写本地幂等记录或条件更新。
- 事件载荷版本化，避免后续字段演进破坏旧消费者。

### 5.3 测试

- 多 worker 抢占、租约过期、重复投递和中断恢复。
- Kafka 消息格式、消费者幂等和失败重试。

## 阶段 6：前端、集成与验收

### 6.1 前端

- 新增处罚规则、处罚单、申诉、退款补偿、发券批次、活动发布任务页面。
- 高风险操作显示确认、当前状态、失败原因和审计信息。
- 前端不将“任务已创建”显示为“下游已执行成功”。

### 6.2 后端集成

- 扩展 `scripts/admin-test`，覆盖全新接口和非破坏性真实联调。
- 启动脚本加入所需 job 和消费者，并避免依赖未构建的二进制。
- 运行 Go 测试、路由 smoke、前端生产构建。

### 6.3 验收标准

- 所有第一期写操作具备权限、审计、幂等和最终状态可查能力。
- 下游不可用时任务不丢失、可重试且不会误报成功。
- 相同事件重复投递不产生重复资金、处罚或发券结果。
- 迁移脚本不自动执行且不修改已有业务数据。

## 实施顺序

按以下顺序提交代码，避免跨模块半成品长期存在：

1. 阶段 0；
2. 阶段 1；
3. 阶段 5 中支持处罚所需的最小 outbox 投递；
4. 阶段 2；
5. 阶段 3；
6. 阶段 4；
7. 阶段 5 的完整重试与消费者能力；
8. 阶段 6。
