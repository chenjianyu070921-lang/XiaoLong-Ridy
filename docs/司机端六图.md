# 司机端六图（2 时序 + 2 流程 + 2 泳道）

> 对应《司机端模板示例两套.md》三套内容 + 机制卡片，全部基于真实代码，可直接在支持 Mermaid 的环境渲染。

---

## 时序图一：司机上线听单 → 派单 → 接单（对应 示例一 GEO key / 示例二 派单）

```mermaid
sequenceDiagram
    autonumber
    participant App as 司机App
    participant GW as api/driver
    participant DS as driversvc
    participant RD as Redis(GEO/在线/busy)
    participant LC as locationsvc
    participant DP as dispatchsvc
    participant OS as ordersvc
    participant WS as WebSocket

    App->>GW: 上线 SetDriverOnline
    GW->>DS: SetDriverOnline
    DS->>RD: 清 busy(clearDispatchDriverBusy) + 写 GEO + 写在线集合
    DS-->>GW: online_status=1
    GW-->>App: 上线成功，开启位置定时上报
    loop 心跳/位置上报
        App->>GW: ReportLocation
        GW->>LC: 写地理位置（只更新 GEO 坐标，不清 busy）
    end
    乘客下单->>OS: CreateOrder
    OS->>DP: DispatchOrder
    DP->>RD: GEO 半径查附近 + 排除 busy 集合
    RD-->>DP: 候选司机（不含服务中司机）
    DP->>WS: 向候选司机推送抢单
    WS-->>App: 收到派单通知
    App->>GW: 接单 AcceptOrder
    GW->>OS: AcceptOrder
    OS->>DS: markDriverBusy（加入 busy 集合）
    OS-->>GW: 订单 Accepted，进入接驾
```

**代码出处**：`rpc/driversvc/internal/logic/set_driver_online_logic.go`（只在上线清 busy）、`dispatch_availability.go`（syncDispatchDriverOnline 只同步不清除 busy）、`rpc/ordersvc/internal/logic/accept_order_logic.go`（markDriverBusy）。

## 时序图二：提现申请 → 后台审核 → 打款（对应 示例一 提现防资损）

```mermaid
sequenceDiagram
    autonumber
    participant App as 司机App
    participant GW as api/driver
    participant DS as driversvc
    participant DB as MySQL
    participant AD as adminsvc
    participant BK as 银行通道

    App->>GW: 发起提现 CreateWithdraw(银行卡, 提现密码, 金额)
    GW->>DS: CreateWithdraw
    DS->>DS: 校验密码(bcrypt) + 本人卡实名一致 + 金额有限值/两位小数
    DS->>DB: 生成提现单 WDxxx，状态=申请中(1)
    DS-->>GW: 返回提现单号（密码仅首次返回）
    GW-->>App: 申请成功
    AD->>AD: 运营审核 AuditWithdraw
    alt 审核通过
        AD->>DB: 置状态 2 打款成功，写打款时间
        AD->>BK: 真实打款
        BK-->>AD: 打款回执
    else 审核驳回
        AD->>DB: 置状态 3 打款失败，备注必填
    end
```

**代码出处**：`rpc/driversvc/internal/logic/create_withdraw_logic.go`（校验+生成单+状态 1）、`rpc/driversvc/proto/driversvc.proto`（AuditWithdraw：approve=true 置 2 打款，false 置 3）。

## 流程图一：行程订单状态机（对应 示例三 状态机非法跃迁）

```mermaid
flowchart TD
    S0([初始创建 0]) --> WA{待接 WaitAccept}
    WA -->|司机接单| AC[接驾 Accepted]
    WA -->|超时未接/乘客取消| CA[已取消 Cancelled]
    AC -->|到达上车开始行程| OT[行程中 OnTrip]
    AC -->|司机或乘客取消| CA
    OT -->|到达目的地| WP[待支付 WaitPay]
    WP -->|乘客支付完成| CO[已完成 Completed]
    CO -->|发起退款| RF[已退款 Refunded]
    CA --> END1([终态 不再流转])
    RF --> END2([终态 不再流转])
```

**讲点**：所有流转过 `CanTransit` 集中校验，`OnTrip` 之后只能到 `WaitPay`，禁止跳状态。
**代码出处**：`rpc/ordersvc/internal/logic/state_machine.go`。

## 流程图二：busy 生命周期与防重复派单（对应 示例二 重复派单）

```mermaid
flowchart TD
    A[司机上线 SetDriverOnline] --> B[清 busy + 写 GEO + 在线集合]
    B --> C[心跳/位置上报：仅更新 GEO 坐标，不清 busy]
    C --> D{是否收到派单?}
    D -->|否，继续听单| C
    D -->|是| E[司机接单 AcceptOrder]
    E --> F[markDriverBusy 加入 busy 集合]
    F --> G[派单引擎查候选时排除 busy 集合]
    G --> H[该司机不再被重复派单]
    E --> I[行程结束 / 下线 / 被踢]
    I --> J[SRem 在线 + ZRem GEO + 清 busy]
    J --> K([重新可被派单])
```

**讲点**：busy 是防重复派单的核心开关——只在「上线」清除，心跳/上报不清除；接单加入 busy；下线/被踢才清理。原 `Pipelined` 批量写会静默丢 `ZREM/SREM`，已改为逐条 `SRem/ZRem`。
**代码出处**：`dispatch_availability.go`（clearDispatchDriverBusy 仅上线调用、离线逐条 SRem/ZRem）、`set_driver_online_logic.go`、`accept_order_logic.go`（markDriverBusy）。

## 泳道图一：提现防资损（对应 示例一 提现）

```mermaid
flowchart TD
    subgraph 司机
        A1[发起提现申请] --> A2[选择本人已绑银行卡]
        A2 --> A3[输入平台提现密码]
    end
    subgraph driversvc司机服务端
        B1[校验密码 bcrypt] --> B2[校验卡为本人且实名一致]
        B2 --> B3[金额校验 有限值/两位小数]
        B3 --> B4[生成提现单 WD+时间+随机<br/>状态=申请中(1)]
    end
    subgraph adminsvc管理后台
        C1[运营审核 通过/驳回] --> C2{approve?}
        C2 -->|通过| C3[置状态 2 打款成功<br/>写打款时间]
        C2 -->|驳回| C4[置状态 3 打款失败<br/>备注必填]
    end
    subgraph 银行通道
        D1[真实打款]
    end
    A3 --> B1
    B4 --> C1
    C3 --> D1
```

**讲点**：司机侧只「发起+记录」，打款由 adminsvc 审核后置状态；防超量公式「可用余额 = 总收入 − 已申请 − 已打款」。
**代码出处**：`create_withdraw_logic.go`、`driversvc.proto`（AuditWithdraw）。

## 泳道图二：重复派单多角色协作（对应 示例二 重复派单）

```mermaid
flowchart TD
    subgraph 司机App
        A1[上线] --> A2[心跳上报位置]
        A2 --> A3[接单]
        A3 --> A4[行程结束/下线/被踢]
    end
    subgraph api-driver
        B1[转发上线/上报/接单请求]
    end
    subgraph driversvc
        C1[清 busy + 写 GEO + 在线集合] --> C2[仅更新 GEO 坐标，不清 busy]
        C2 --> C3[接单 markDriverBusy 加入 busy]
        C3 --> C4[下线/被踢: SRem 在线 + ZRem GEO + 清 busy]
    end
    subgraph dispatchsvc
        D1[GEO 半径查附近候选] --> D2[排除 busy 集合]
        D2 --> D3[向剩余候选推送抢单]
    end
    subgraph Redis
        E1[(driver:geo:default)]
        E2[(driver:online)]
        E3[(driver:busy)]
    end
    A1 --> B1 --> C1
    A2 --> B1 --> C2
    C1 --> E1 & E2 & E3
    A3 --> B1 --> C3
    C3 --> E3
    A4 --> B1 --> C4
    C4 --> E1 & E2 & E3
    D1 --> E1
    D2 --> E3
    D3 --> A3
```

**讲点**：跨 5 个角色（司机App / 网关 / driversvc / dispatchsvc / Redis）的协作闭环；busy 集合是「派单引擎排除服务中司机」的唯一依据，任何角色误清 busy 都会造成重复派单。
**代码出处**：`dispatch_availability.go`、`set_driver_online_logic.go`、`accept_order_logic.go`、`dispatchsvc`。
