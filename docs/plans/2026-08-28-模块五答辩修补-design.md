# 模块五答辩修补 design（2026-08-28）

> 组长今日 P0 三件事：① api 层补支付回调 HTTP 路由；② CreatePayment 真实渠道接入校验；③ 对账/分账结构补全。
> 本文档是修补方案设计，与现有架构（go-zero zrpc + api 网关层）保持一致。

## 0. 现状摘要（2026-08-28）

| 缺口 | 现状 | 关键文件 |
|---|---|---|
| **① api 网关层缺支付回调 HTTP 路由** | `api/admin`、`api/passenger`、`api/driver` 三个网关层都没有 `/api/pay/callback/*` 入口；回调当前挂在 paysvc 进程内（`httpAddr: 8888`），公网打不到 rpc 端口 | `api/admin/internal/handler/router.go` 已有的路由风格（mux + authRequired + writeSuccess） |
| **② CreatePayment 真实渠道未接** | `channel/alipay.go` 真实实现已完整；`GetChannel` 在密钥齐全时走真实 AlipayChannel，否则降级 Mock；缺启动期硬校验 | `rpc/paysvc/internal/svc/service_context.go` 中 `newAlipayChannel` 静默降级 |
| **③ 对账/分账缺位** | 仅有 Kafka 事件兜底补发（`event_reconcile_job.go`）；缺资金对账、缺自动结算 job | `scripts/sql/migrate/05_trade_module.sql` 无对账表 |

## 1. 设计总览

**三条 P0 的统一原则：结构先就位 + 可运行骨架 + 真实集成点用 TODO 标注，不假装能跑通沙箱。**

## 2. 详细设计

### 2.1 P0 ① — api 层支付回调 HTTP 路由

**新增文件**：`api/admin/internal/logic/pay_callback_logic.go`

```go
// 思路：
// 1. 解析 application/x-www-form-urlencoded 表单
// 2. 透传给 paysvc.NotifyPayment（gRPC），用 proto 已生成的 client
// 3. RPC 返回 success=true → 写 "success"；其余 → 写 "fail"
// 4. 表单解析失败 / RPC 调用失败 / RPC 返回 success=false → 一律写 "fail"，触发支付宝重试
type PayCallbackLogic struct {
    ctx *svc.ServiceContext
    logx.Logger
}

func (l *PayCallbackLogic) HandleAlipayNotify(req *http.Request) (string, error) {
    if err := req.ParseForm(); err != nil {
        return "fail", err
    }
    raw := buildNotifyRaw(req.Form) // out_trade_no / trade_no / total_amount / gmt_payment
    paymentNo := req.FormValue("out_trade_no")
    if paymentNo == "" {
        return "fail", errors.New("missing out_trade_no")
    }
    resp, err := l.ctx.PayClient.NotifyPayment(l.ctx, &proto.NotifyPaymentRequest{
        PaymentNo:        paymentNo,
        TradeStatus:      req.FormValue("trade_status"),
        TransactionId:    req.FormValue("trade_no"),
        TotalAmountCents: priceutil.YuanStringToCents(req.FormValue("total_amount")),
        PaidAt:           parseAlipayTime(req.FormValue("gmt_payment")),
        NotifyRaw:        raw,
    })
    if err != nil || resp == nil || !resp.Success {
        return "fail", nil
    }
    return "success", nil
}
```

**router 改动**（`api/admin/internal/handler/router.go`）：

```go
// 注意：不走 authRequired（支付宝回调不带 token），用 IP 白名单中间件或网关上 Nginx 限源。
r.mux.HandleFunc("/api/pay/callback/alipay", r.handleAlipayCallback)
```

```go
func (r *Router) handleAlipayCallback(w http.ResponseWriter, req *http.Request) {
    if req.Method != http.MethodPost {
        w.WriteHeader(http.StatusOK)
        _, _ = w.Write([]byte("fail"))
        return
    }
    body, err := logic.NewPayCallbackLogic(r.ctx).HandleAlipayNotify(req)
    // 不论成功失败都返回 200，body=success/fail（支付宝协议）
    w.Header().Set("Content-Type", "text/plain; charset=utf-8")
    w.WriteHeader(http.StatusOK)
    _, _ = w.Write([]byte(body))
    _ = err // 失败时已写 "fail"，调用方日志由中间件记录
}
```

**为什么挂在 api/admin 而不是 api/passenger**：
- admin 已配置 `AdminRPCClient`，新增 `PayClient` 复用同样的 zrpc 客户端模式；
- admin 已有 mux + writeJSON + 错误处理工具（直接复用 writeSuccess/writeError，但回调必须写 text/plain，不能用 writeJSON）；
- 不挂 passenger 是因为 passenger api 只接乘客侧的 SMS/登录，没有 gRPC 客户端基础设施；
- 不挂 driver 同理。

**ServiceContext 改动**：在 `api/admin/internal/svc/servicecontext.go` 中新增 `PayClient paysvcclient.PayService` + 初始化代码（复用 `zrpc.MustNewClient`）。

**paysvc 进程自带 httpAddr 怎么处理**：
- 保留，不删除（`paysvc.go` 行 60–70 的 HTTP 监听保留）；
- 文档说明："admin 网关是主路径，paysvc 自带 HTTP 仅为本地 dev 模式快速联调（不走网关直连）"；
- 这样 dev 模式不需要先启动 admin 网关，符合既有 e2e 测试 `scripts/e2e/pay_e2e_client.go` 的调用方式。

### 2.2 P0 ② — CreatePayment 真实渠道硬校验

**现状回顾**：`newAlipayChannel` 在密钥不齐时仅 logx.Info 然后 return nil，`GetChannel` 静默降级为 Mock。生产环境如果 yaml 没填密钥，paysvc 会"假装上线"但调用 mock 渠道生成假 transaction_id —— 真实资金流断链。

**修补策略（M5-12，mode 感知，与 newVerifier 语义对称）**：

- **生产模式**（mode 为空）：缺核心三件套 → **立即返回 error**，paysvc 启动失败，强制运维配置；
- **dev/test 模式**：允许渠道降级 Mock（保留 `paysvc-test.yaml` 本地联调用途，无沙箱密钥也能跑通流程）；
- `GetChannel`：生产模式直接返回真实 AlipayChannel，不再做 mock 兜底；dev/test 且 alipayChannel 为 nil 时才降级。

**改动**（`rpc/paysvc/internal/svc/service_context.go`）：

```go
// newAlipayChannel 创建支付宝真实渠道（M5-12，mode 感知）。
func newAlipayChannel(a alipay.Config, mode string) (*channel.AlipayChannel, error) {
    if !a.HasRealKeys() {
        if mode == service.TestMode || mode == service.DevMode {
            logx.Info("alipay keys missing, channel will fallback to mock (dev/test mode only)")
            return nil, nil // dev/test 允许降级，保持本地联调可用
        }
        return nil, errors.New("alipay keys missing: appId/privateKey/alipayPublicKey must all be set; mock fallback is not allowed (M5-12)")
    }
    resolved := a.WithDefaults()
    ch, err := channel.NewAlipayChannel(resolved)
    if err != nil {
        return nil, fmt.Errorf("init alipay channel: %w", err)
    }
    logx.Info("alipay real channel enabled")
    return ch, nil
}
```

```go
// GetChannel：生产模式直接返回真实渠道，dev/test 且渠道为 nil 时降级 Mock。
func (s *ServiceContext) GetChannel(name string) channel.PayChannel {
    if name == channel.Alipay && s.alipayChannel != nil {
        return s.alipayChannel
    }
    return channel.NewMockChannel(name)
}
```

**配置文档更新**（`docs/module5/联调记录.md`）：新增"支付渠道配置说明"小节，列出 yaml 与 env 两种注入方式 + 沙箱/生产密钥获取地址 + mode 语义。

## 5. 风险与权衡

- **回调挂 admin 网关**而不是新建 `api/pay` 服务：少一个进程、复用现有 admin infra；权衡：admin 网关挂了支付回调也挂（但 admin 本来就是网关，多挂一个路由影响小）。
- **对账/分账只做骨架**：时间紧 + 无沙箱账号，骨架就位 + 答辩可讲；权衡：未来真接入需补充 `channel.AlipayClient.QueryTrade` + 完整差异修复流程。
- **不动既有 GetChannel 余额渠道**：余额扣减是账户体系，本次范围外。
