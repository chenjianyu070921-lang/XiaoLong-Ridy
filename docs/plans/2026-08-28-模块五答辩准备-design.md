## 4. .docx 答辩稿大纲（D1）

> 风格：标题 1/2/3 + 表格 + 有序列表；每章末尾「口述要点」段落用粗体小标题提示讲什么。

1. **封面**：模块五答辩稿 / 姓名 / 日期 / 分支
2. **摘要（一句话项目定位）**
3. **项目架构**：模块五在 6 模块中的位置 + 全项目微服务图
4. **项目一览**：功能结构图 + 业务流程图 + 泳道图
5. **本组本月负责项目**：模块五范围 + 本人负责子模块
6. **项目背景 + 讲解需求**：
   - 业务背景（网约车计价/支付的特殊性）
   - 需求来源（订单模块、乘客端需求）
   - 计价与支付的关键问题（夜间/高峰/优惠叠加/支付幂等/退款一致性）
7. **需求分析方法论**：
   - 原型图分析维度（信息架构/业务流/异常流/边界条件/可测性）
   - 拿到原型后的工作清单（澄清问题 / 拆任务 / 排期 / 评审）
8. **功能实现路径**：
   - DDL → proto → rule 引擎 → logic 层 → channel 抽象 → 测试
   - TDD 节奏（每个 rpc 一个单测文件）
9. **技术方案**：
   - 表对比：金额「分」vs「元」/decimal、GORM vs raw sql、IBM/sarama vs segmentio 等
10. **讲解难点 + 难点如何解决**：
    - 难点 1：跨天夜间判断（23:00-05:00）— 单测驱动
    - 难点 2：支付回调幂等（重复回调不落库）— payment_no 唯一 + 状态机
    - 难点 3：金额精度（避免 float 漂移）— priceutil/Add + math.Round
    - 难点 4：跨服务协作（订单模块 GetOrder + order.paid Kafka）
11. **项目优化（核心结合 AI）**：
    - 优化前 / 优化后对比表：演示页 JS 复刻 vs 复用真实引擎 / 跨服务复用 internal 的坑
12. **测试结果**：单测覆盖率（待执行后填入）+ e2e 联调脚本 + 截图
13. **发布上线流程 + Linux + 多服务**：`deploy/docker/infra.yml` + `go run` / `docker compose up`
14. **后期监控规划**：Kafka lag + payment_status=3 告警 + 演示页内置模式 fallback
15. **AI 防幻觉措施**：8 条具体举措（自带手动抽查脚本、双向交叉验证、real-service 优先级、查 memory、pre-mortem 等）
16. **答辩口述稿分段话术**：自我介绍 / 项目背景 / 讲解需求 / 难点 / 解决 / 优化 / 测试 / 上线 / 监控 / AI 部分预留 / 结束语 / 自我总结
17. **附录 A：图表清单**（指向 D2）
18. **附录 B：答辩常见追问清单**（怕老师问什么，提前准备 20 个 Q&A）

## 6. 防幻觉措施（要嵌入 .docx 第 15 章）

> 这些是「具体怎么不胡说」，老师爱问。

1. **金额手算举例每张表必给**。任何表格 "X 元" 都附 "计算过程：1200+2375+1500=5075 分=50.75 元"。
2. **接口名/字段名直接照抄源码**。`.docx` 里所有 proto 字段与 `rpc/*/proto/*.proto` 一致，必要时附 `code ../proto/xxx.proto:Lxx` 行号定位。
3. **图表渲染与代码实跑对账**。演示页跑通后，把 5 个期望值表格化"贴在文档 + 现场再跑一次"。
4. **跨服务协作点留"对接文档"指针**。如 `docs/module5/给成员4的对接说明.md`，避免 AI 凭印象编"订单模块如何调我"。
5. **不写没做过的功能**。`docs/plans` 三份设计文档规定了什么做了、什么延后（比如优惠券落库、对账报表），文档严守这条边界。
6. **"嘴替版"代码引用**：所有引用的代码段必须能在 `git grep` 找到，否则改写。
7. **现场演示兜底**：内置模拟模式（演示页 .html 直接双击也能讲），避免"现场服务挂了翻车"。
8. **保留老师会问的"扣分点"清单**：内部可见问题（ordersvc.GetOrder 仍空壳、refund 上层联动缺）老实承认，不包装。
