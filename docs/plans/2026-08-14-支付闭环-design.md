# 模块五：支付闭环设计文档

日期：2026-08-14
分支：module5-qyx
前序：2026-08-13 已完成 pricesvc/paysvc 骨架 + 三个核心接口（EstimatePrice/CalculateDiscount/CreatePayment）

## 一、今日目标

打通支付正向主流程闭环：**支付成功回调 → 更新支付单 → 发 Kafka 事件 → 触发司机结算 → 查询支付结果**；同时补齐计价规则扩展与底层退款接口。

## 二、今日范围（做 / 不做）

### 做
1. **支付回调** `NotifyPayment`：支付宝回调验签 → 更新 payment 状态为「支付成功」→ 回填流水号/支付时间 → 发 Kafka「支付成功」事件 → 调 ordersvc.GetOrder 拿 driver_id → 触发司机结算
2. **司机结算** `SettleOrder`：计算平台抽成 + 司机实收 → 写 settlement 表
3. **支付查询** `GetPayment`：按支付单号/订单ID查支付状态
4. **退款** `RefundPayment`：支付单状态变更 + refund_amount 回写 + 渠道 mock 退款（独立自测跑通）
5. **计价规则扩展**：高峰溢价（rule 引擎）

### 不做（延后）
- 订单取消联动触发退款的**上层调用链路**（等订单模块/成员4配合）
- order-event-consumer 消费者实现（属于成员4，我只发消息 + 留约定）

## 三、技术决策（已与用户确认）

| 决策点 | 选择 |
| --- | --- |
| Kafka 库 | IBM/sarama |
| 支付宝签名校验 | 引入官方 SDK（smartwalle/alipay/v3）做真实验签 |
| 结算 driver_id 来源 | 支付回调后调 ordersvc.GetOrder 获取 |
| 金额单位 | 延续昨日约定：接口/计算用「分」(int64)，DB 存 decimal 元 |
| 支付渠道 | channel 抽象层，退款/回调均走 mock（签名校验除外，用真实 SDK） |

## 四、新增 proto 接口设计

### paysvc.proto 新增 4 个 rpc

```proto
service Pay {
  rpc CreatePayment(CreatePaymentRequest) returns (CreatePaymentResponse); // 已有
  rpc NotifyPayment(NotifyPaymentRequest) returns (NotifyPaymentResponse); // 新增：支付回调
  rpc GetPayment(GetPaymentRequest) returns (GetPaymentResponse);           // 新增：支付查询
  rpc RefundPayment(RefundPaymentRequest) returns (RefundPaymentResponse);  // 新增：退款
  rpc SettleOrder(SettleOrderRequest) returns (SettleOrderResponse);        // 新增：司机结算
}
```

### NotifyPayment（支付宝回调）
```proto
message NotifyPaymentRequest {
  string payment_no = 1;      // 平台支付单号
  string trade_status = 2;    // 支付宝交易状态：TRADE_SUCCESS/TRADE_CLOSED 等
  string transaction_id = 3;  // 第三方流水号
  string sign = 4;            // 支付宝签名
  string sign_type = 5;       // 签名类型 RSA2
  int64 paid_at = 6;          // 支付时间（Unix 秒）
  string notify_raw = 7;      // 原始回调参数（验签用，可 JSON 串）
}

message NotifyPaymentResponse {
  bool success = 1;
  string message = 2;
}
```

### GetPayment（查询）
```proto
message GetPaymentRequest {
  string payment_no = 1; // 按支付单号查（优先）
  int64 order_id = 2;    // 或按订单ID查
}

message GetPaymentResponse {
  int64 payment_id = 1;
  string payment_no = 2;
  int64 order_id = 3;
  int64 amount_cents = 4;
  string channel = 5;
  int32 status = 6;        // 1待支付 2支付成功 3支付失败 4已退款
  string transaction_id = 7;
  int64 refund_amount_cents = 8;
}
```

### RefundPayment（退款）
```proto
message RefundPaymentRequest {
  string payment_no = 1;
  int64 refund_amount_cents = 2; // 退款金额（分）
  string reason = 3;
}

message RefundPaymentResponse {
  bool success = 1;
  string refund_no = 2;         // 退款单号（mock）
  int64 refunded_amount_cents = 3; // 累计已退款金额
}
```

### SettleOrder（司机结算）
```proto
message SettleOrderRequest {
  int64 order_id = 1;
  int64 driver_id = 2;          // 司机ID（回调链路中由 ordersvc.GetOrder 取得）
  int64 total_amount_cents = 3; // 订单实际总金额（分）
  double commission_rate = 4;   // 平台抽成比例（%，如 20 表示 20%）
}

message SettleOrderResponse {
  int64 settlement_id = 1;
  string settlement_no = 2;
  int64 platform_commission_cents = 3; // 平台抽成
  int64 driver_income_cents = 4;       // 司机实收
}
```

### 5.4 支付回调链路（核心）
```
支付宝回调
  → NotifyPayment
    → 验签（alipay SDK，失败返回错误）
    → 查 payment（by payment_no）
    → 校验状态（仅「待支付」可流转为「支付成功」）
    → 更新 payment：status=2, transaction_id, paid_at
    → 发 Kafka 消息 order.paid（order_id, payment_no, amount）
    → 调 ordersvc.GetOrder 拿 driver_id
    → 调 SettleOrder 生成结算单
```

### 5.5 司机结算公式
```
platform_commission = total_amount × commission_rate / 100
driver_income = total_amount - platform_commission
```
- 结算单号 `settlement_no` 生成规则对齐 payment_no 风格
- 结算状态：1待结算 → 2已结算（本期直接写「已结算」）

### 5.6 退款（底层接口，独立自测）
```
RefundPayment
  → 查 payment（by payment_no）
  → 校验状态（仅「支付成功」可退款）
  → 调 channel mock 退款
  → 更新 payment：status=4(已退款), refund_amount += 退款金额
  → 返回退款结果
```
- 上层「订单取消联动退款」延后，本期仅保证底层接口可独立自测

### 5.7 计价规则扩展：高峰溢价
- rule 引擎新增高峰时段判断 + 高峰溢价费项
- 高峰时段：早高峰 07:00-09:00、晚高峰 17:00-19:00（可配置）
- 高峰溢价金额：复用动态调价机制（factor），或独立 `peak_surcharge` 计费项
- 设计取舍见「待确认」

## 六、数据流

```
行程结束(ordersvc) → 创建支付单(CreatePayment) → 乘客支付 → 支付宝回调
  → NotifyPayment(验签) → payment.status=支付成功
    → Kafka: order.paid ──→ order-event-consumer(成员4，延后)
    → ordersvc.GetOrder(driver_id)
    → SettleOrder → settlement 落库
乘客查询 → GetPayment → 支付状态
订单取消(延后) → RefundPayment → payment.status=已退款
```

## 七、风险与依赖

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| ordersvc.GetOrder 是空壳 | 今日联调 driver_id 会返回 0 | OrderClient 接口化 + 单测 mock；真实联调等成员4补全 |
| Kafka 容器未启动 | sarama 发送会失败 | 生产者封装容错；发送失败仅记日志不阻断主流程 |
| 支付宝 SDK 验签需要真实公钥 | 无真实公钥时验签会失败 | 验签抽象成接口，mock 实现可切 |

## 八、待确认（可后续调整）
1. **高峰溢价实现方式**：建议复用「动态调价 factor」机制（高峰时段 factor 自动上调），不新增 DB 字段、不新增独立计费项。若组长要求独立「高峰附加费」字段，需改 price_rule 表 DDL。
2. **Kafka 主题名**：`order.paid`（与 ordersvc 已配置的 `order.created` 风格一致）。
