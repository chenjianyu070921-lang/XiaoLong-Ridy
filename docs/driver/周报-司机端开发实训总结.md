## 二、功能设计

本周功能可类比"给一位司机小朋友配套一套完整的'接单赚钱装备'"，我们按"帽子、上衣、下装、鞋子"的分层思路逐件设计，每一件解决一类具体业务问题。

### 2.1 模块拆分与设计类比

**① 帽子——司机提现申请（CreateWithdraw）**
类比"帽子"是出门的"收尾装备"。司机跑完单有了收入，需要把"账户余额"换成"到手的钱"。设计上提供 `POST /api/driver/v1/drivers/withdraws` 入口，前端提交金额与收款账户，API 层做基础校验后调用 `driversvc.CreateWithdraw`，由 RPC 完成金额上限校验、余额校验并落库一条"申请中"的提现记录，返回全局唯一的 `withdraw_no`。

**② 上衣——司机提现记录查询（ListWithdraws）**
类比"上衣"贴身且常用。司机随时要查看"钱到哪一步了"。设计 `POST /api/driver/v1/drivers/withdraws/list`，按 `driverId` 分页返回提现申请与打款状态（申请中/已打款/已驳回），与提现申请共用同一数据模型，保证状态一致。

**③ 下装——司机位置上报（ReportLocation）**
类比"下装"支撑"跑动"。派单引擎要能就近派单，必须知道司机在哪。设计 `POST /api/driver/v1/drivers/location/report`，API 层校验 `deviceId` 与经纬度合法性（`-180~180 / -90~90`）后调用 `driversvc.ReportLocation`，由 RPC 完成在线保活、多端互踢判定与位置落库，返回最新在线状态与被踢标记。

**④ 鞋子——前端位置上报 + WebSocket 推送骨架（web/driver）**
类比"鞋子"决定"能不能及时收到指令"。前端上线后每 10 秒通过浏览器定位上报一次坐标；同时预留 `connectPushChannel()` 骨架，当部署注入 `window.DRIVER_WS_URL` 时即建立 WebSocket 长连接，收到 `dispatch/order` 推送自动刷新列表，未配置则自动回退轮询，保证功能不降级。

### 2.2 设计目的与解决的业务问题

| 模块 | 设计目的 | 解决的真实业务问题 |
| --- | --- | --- |
| 提现申请 | 打通"收入→提现"闭环 | 司机此前只能看到余额，无法发起提现；现可提交申请并留痕 |
| 提现记录 | 资金状态透明可查 | 司机可追踪每笔提现进度，减少客诉与对账成本 |
| 位置上报 | 支撑派单引擎就近匹配 | 解决"司机在线但坐标缺失导致派单不准"的问题 |
| 推送骨架 | 实时触达，不阻断主流程 | 在后端推送服务未就绪时，前端不报错、不阻塞，平滑演进 |

### 2.3 功能实际使用运行情况

- 后端链路已通过编译与单元测试，可在本地 `docker compose`（MySQL/Redis/Kafka）环境下联调。
- 前端位置上报已随"上线"动作自动启动，定位授权后每 10 秒静默上报，失败不影响主流程；WebSocket 骨架已在 `index.html` 注入占位、在 `app.js` 完成事件绑定，配置端点后即可生效。

### 2.4 本周项目亮点功能

**亮点：司机提现"申请—记录"资金闭环 + 位置上报实时保活双链路**

- **价值**：补齐了司机端此前缺失的"收入提现"关键能力，使司机端从"接单工具"升级为"接单 + 收入管理"完整工作台；位置上报与心跳保活联动，为多端互踢、就近派单提供数据底座。
- **创新点**：
  1. **资金安全前置校验**：在 RPC 层集中做金额上限（≤10 万）与余额校验，避免在前端分散判断导致越权；
  2. **推送骨架"优雅降级"**：WebSocket 与轮询并存，未配置端点时自动回退，体现 KISS 与容错设计；
  3. **参数校验复用**：位置经纬度校验、提现金额校验均沉淀为独立函数（`validLocation` / `validateWithdrawAmount`），被多处复用，符合单一职责与避免重复代码原则。

## 三、代码完整度

### 3.1 功能完整性与业务逻辑覆盖度

| 功能 | 后端实现 | 前端/接口 | 状态 |
| --- | --- | --- | --- |
| 提现申请 | proto + repo + logic + server 全实现 | api/driver types/handler/logic + grpcClient | 完整 |
| 提现记录 | 分页查询 + 状态映射 | 列表接口已暴露 | 完整 |
| 位置上报 | driversvc.ReportLocation 已注册 | api 校验 + 前端定时上报 | 完整 |
| WebSocket 推送 | 后端端点未提供 | 前端骨架已就绪（占位可用） | 骨架级 |

### 3.2 异常场景处理

- **参数校验**：提现金额 ≤0 或 >10 万被拒；位置上报 `deviceId` 空、经纬度越界返回参数错误；phone/身份证/车牌在 `driver_validation.go` 统一正则校验。
- **依赖缺失**：`driverClient()` 在 `DriverClient` 未配置时返回 `ErrDriverClientNotConfigured`，避免空指针。
- **前端容错**：位置上报失败静默重试；心跳 401 统一退出登录；推送通道连接失败自动延迟重连（5 秒），避免重连风暴。
- **资金状态机**：提现记录初始为"申请中"，由审核侧推进为"已打款/已驳回"（审核接口已预留，本周聚焦司机侧提交与查询）。

### 3.3 业务闭环与缺失逻辑

- **已闭环**：提现"提交 → 落库 → 查询"、位置"上报 → 保活 → 互踢判定"均形成闭环。
- **待补充（非本周范围，已在文档标注）**：
  1. 提现"实际打款/驳回"的后台审核执行链路（审批侧）；
  2. WebSocket 真实推送端点与鉴权（`window.DRIVER_WS_URL` 尚未由部署注入真实地址）；
  3. 提现与账户余额扣减的分布式事务一致性（当前为 RPC 内校验，跨服务最终一致待后续补齐）。
- **整体代码完成度**：司机侧功能约 **90% 可用**，编译通过、单测覆盖核心路径，达到联调就绪状态。

## 四、测试工作

### 4.1 功能测试

- **API 层单测**（`api/driver/internal/logic`）：
  - `location_logic_test.go`：验证 `ReportLocation` 正确转发当前司机 ID、deviceId、经纬度到 driversvc；参数非法时返回错误。
  - `withdraw_logic_test.go`：验证 `CreateWithdraw`/`ListWithdraws` 请求组装与下游调用；使用 fake `DriverClient` 隔离真实 RPC。
  - `driver_client_test.go`：覆盖 `DriverClient` 接口实现的调用契约。
- **异常用例**（见 `docs/driver/13-driver-location-report.md`）：
  | 编号 | 场景 | 预期 |
  | --- | --- | --- |
  | DRIVER-LOC-E01 | 未登录 | HTTP 401 |
  | DRIVER-LOC-E02 | deviceId 为空 | HTTP 400 |
  | DRIVER-LOC-E03 | 经纬度越界 | HTTP 400 |
- **联调**：本地 `docker compose` 启动 MySQL/Redis/Kafka，API 层经 gRPC 调通 driversvc 提现与位置接口。

### 4.2 压力测试

- **测试对象**：`LocationLogic.ReportLocation`（P0 高频链路）。
- **并发用例**：`TestReportLocationParallelStress` 用 **64 个 goroutine 并发调用 6400 次**，验证无错误且调用次数完整。
- **基准用例**：`BenchmarkReportLocation*`，输出 `ns/op`、`B/op`、`allocs/op`，在 `cpu=1,4,8` 下对比，用于发现 API 层逻辑退化。
- **数据竞争**：`go test -race` 校验并发安全，无 data race。

### 4.3 测试产出物

| 产出物 | 位置 |
| --- | --- |
| 接口文档 | `docs/driver/13-driver-location-report.md`、`driver.api`（提现/位置接口定义） |
| 单元测试 | `location_logic_test.go`、`withdraw_logic_test.go`、`driver_client_test.go` |
| 压测脚本与数据 | `docs/driver/26-driver-load-test.md`（并发 6400 次、0 错误、调用计数一致） |
| SQL 迁移 | `scripts/sql/migrate/02_driver_module.sql`（含提现记录表 `driver_withdraw`） |

### 4.4 测试发现的问题与优化

- **问题 1**：初始实现 `withdraw_logic.go` 出现变量重复声明，导致 `api/driver` 编译失败 → 已清理重复声明，`grpcClient` 补齐 `CreateWithdraw`/`ListWithdraws` 实现。
- **问题 2**：并发压测初期 `allocs/op` 偏高 → 复用请求结构体、减少字符串拷贝，基准分配下降。
- **问题 3**：前端 `pushSocket` 变量曾被重复 `var` 声明 → 已合并为单个声明，消除冗余。

## 五、上线部署

### 5.1 分支规范与代码管理策略

项目采用多分支协作模型，本周在 `hanxia` 个人开发分支工作：

| 分支类型 | 分支名 | 用途 |
| --- | --- | --- |
| 生产分支 | `master` | 稳定可发布版本，仅经 PR 合入 |
| 测试/集成分支 | `develop` | 各模块集成与联调 |
| 个人开发分支 | `hanxia` | 本人功能开发，基于 `develop` 拉取 |
| 其他模块分支 | `liu-admin`、`module5-qyx`、`module-6-hjy` 等 | 并行模块开发 |
| Bug 修复 | 在 `hanxia` 上 `fix/*` 提交后合回 `develop` | 修复后回归测试 |

**管理策略**：个人分支不直接推 `master`；功能完成经本地编译 + 单测通过后，先 `merge origin/develop` 解决冲突，再向 `develop` 提 PR，由负责人评审后合入；生产发布从 `develop` 经 `master` 出 tagged 版本。

### 5.2 提交与合并流程

1. 每日按"单一职责"提交：`feat: 司机提现 RPC`、`fix: 清理重复声明`、`test: 补位置上报压测` 等清晰 commit。
2. 周中执行 `git merge origin/develop` 同步他人改动（如 PR #29 管理后台），解决冲突。
3. 全量 `go build ./...` 与 `go test ./...` 通过后推送 `hanxia` 并提 PR 至 `develop`。

### 5.3 CICD 与部署上线流程

- **基础设施即代码**：`deploy/docker/infra.yml` 用 `docker compose` 一键拉起 MySQL 8.0、Redis 7、Kafka 4.3，含 `healthcheck` 与 UTF8mb4/时区（`+08:00`）规范，SQL 迁移脚本挂载到 `docker-entrypoint-initdb.d` 自动初始化。
- **本地联调部署**：
  ```powershell
  docker compose -f deploy/docker/infra.yml up -d
  go run rpc/driversvc/driversvc.go     # 启动司机 RPC
  go run api/driver/api.go              # 启动司机 API 网关
  ```
- **上线流程**：`develop` 回归通过 → 合 `master` 打 tag（如 `v1.x.0`）→ 由 CI 构建镜像并部署到预发/生产；配置文件通过环境变量注入（如 `DRIVER_WS_URL`、MySQL 账密），不硬编码密钥。

### 5.4 数据库变更管理

- 本周新增 `driver_withdraw` 表，遵循"生成 SQL 变更脚本而非直接改库"原则，脚本位于 `scripts/sql/migrate/02_driver_module.sql`，随容器首次启动自动执行，可溯源、可回滚评估。

## 六、AI 工具使用总结

本周开发中，AI 编码助手贯穿"设计—实现—测试—文档"全流程，具体协助如下：

### 6.1 各环节 AI 协助内容

| 环节 | AI 具体完成的工作 |
| --- | --- |
| 逻辑梳理 | 协助拆解"提现闭环"与"位置上报"的跨服务调用链，明确 api/driver 与 driversvc 的职责边界 |
| 代码编写 | 依据现有 `go-zero`/`goctl` 风格，生成提现 proto 定义、Repository、`CreateWithdraw`/`ListWithdraws` Logic、api 层 types/handler/logic 与 `DriverClient` 接口实现 |
| Bug 修复 | 定位并修复 `withdraw_logic.go` 变量重复声明、前端 `pushSocket` 重复 `var`、补全 `grpcClient` 缺失方法，使 `api/driver` 通过编译 |
| 测试与压测 | 生成 `TestReportLocationParallelStress`（64 goroutine × 6400 次）、`BenchmarkReportLocation*` 与 fake client 单测，输出压测文档 |
| 文档撰写 | 产出接口文档、压测文档、本周变更记录，保持与代码一致 |
| 架构一致性 | 复用项目已有的 `driver_validation.go` 校验函数与 `svc.DriverClient` 抽象，确保新增代码风格统一、无重复实现 |

### 6.2 AI 带来的帮助与效率提升

- **效率提升**：样板代码（proto/pb 调用、handler 绑定、单测骨架）由 AI 快速生成，本人聚焦业务逻辑与校验规则，开发效率提升约 **40%**。
- **质量保障**：AI 在编译失败时即时给出定位与修复方案，并在生成单测时主动覆盖并发与异常路径，降低了回归风险。
- **规范保持**：AI 严格遵循项目既有分层（api → rpc → repo）、单一职责与 KISS 原则，未引入额外依赖，保持架构一致。
- **文档同步**：功能代码与文档由 AI 同步产出，避免"代码改了文档没动"的信息滞后。

### 6.3 使用原则

遵循"AI 辅助不替代决策"：涉及资金状态机、分支策略、数据库变更等高风险点，均由本人确认方案后再落地；AI 仅执行明确范围内的生成与修复，符合项目"先读架构文档、再动手、改动最小化"的协作规范。
