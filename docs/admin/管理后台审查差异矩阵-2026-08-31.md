# 管理后台审查差异矩阵

日期：2026-08-31

## 一、文档用途

本文档用于核对部门审查意见与当前仓库实际状态，作为模块三后续整改任务的依据。

本文档只记录分析结论，不修改业务代码、不执行数据库迁移、不改变现有业务数据。

判断依据按以下优先级排列：

1. 当前代码、当前路由和当前测试结果；
2. 最新接口文档与边界文档；
3. 历史测试报告；
4. 面向未来的完整设计文档。

“设计中存在”不等于“当前代码缺失”；“代码中存在”也不等于“已经完成端到端验收”。

## 二、当前事实摘要

| 项目 | 当前事实 | 结论 |
| --- | --- | --- |
| 管理后台 HTTP 网关 | `api/admin` 已注册认证、管理员、用户、司机、订单、优惠券、计价、活动、统计、导出、工单、风控等路由 | 后台入口并非缺失 |
| 管理后台 RPC | `rpc/adminsvc/admin.proto` 已覆盖约 50 个 RPC 方法 | adminsvc 已形成完整业务入口 |
| 司机审核 | 通过 `adminsvc -> driversvc` 执行状态联动 | 已遵循司机域边界 |
| 计价规则 | 通过 `adminsvc -> pricesvc` 读写，后台不直接修改 `price_rule` | 边界基本合理 |
| 统计 | 由 `adminsvc` 基于现有业务表实时聚合 | 没有独立 reportsvc，存在查询扩展性风险 |
| 审计 | 由 `adminsvc` 写 `admin_operation_log`，失败时使用 `admin_audit_outbox` 补偿 | 已有审计机制，但未形成独立 auditsvc |
| 工单 | 由 `adminsvc` 直接管理运营工单表和状态机 | 当前可用，但领域边界集中 |
| 优惠券 | 由 `adminsvc` 直接管理模板和发券任务 | 当前可用，批量发券仍是同步逻辑 |
| 前端 | 多个菜单复用 `web/admin/src/views/console/index.vue` | 有统一工作台，但业务页面深度有限 |
| 测试 | 已有路由冒烟、RPC 逻辑、SQL mock 和失败分支测试 | 代码测试基础较好，仍需真实联调覆盖 |

## 四、已确认的真实问题

### 4.1 P0：导出文档与筛选参数契约不一致

后端代码实际支持 `users`、`drivers`、`orders`、`operation_logs`、`statistics` 五类导出，但旧边界文档曾写成只支持 `orders`；同时前端此前会把不属于当前导出类型的筛选字段一起提交。

风险：

- 文档会误导联调和验收；
- 后端会按筛选白名单拒绝跨类型字段；
- 用户选择合法导出类型后仍可能因无关筛选字段提交而失败。

整改方向：

- 已将边界文档更新为五类真实导出；
- 前端按导出类型提交对应的筛选字段；
- 后续补充五类导出类型的接口和文件生成联调测试。

### 4.2 P0：历史测试结论与当前代码不一致

`docs/admin/管理后台全量接口测试报告-2026-08-18.md` 中的“当前仍未开放路由”包含用户历史、轨迹、人工改派、退款等接口，但当前路由和前端 API 已经出现对应实现。

整改方向：

- 保留历史现场结果；
- 增加 2026-08-31 当前复测结论；
- 明确哪些接口已在后续提交中开放；
- 不用旧报告作为当前能力清单。

### 4.3 P1：统计能力与设计目标存在落差

当前统计由 adminsvc 直接查询业务表，且文档已明确订单缺少权威 `city_code` 字段。

风险：

- 大时间范围查询可能拖慢后台；
- 统计口径依赖多个业务表实时状态；
- 城市筛选无法可靠支持；
- 缺乏数据更新时间和延迟说明。

整改方向：

- 先统一指标定义、时间字段、金额单位和城市限制；
- 增加查询范围限制和失败测试；
- 暂不急于拆分 reportsvc；
- 查询压力确实出现后，再设计独立报表服务或汇总表。

### 4.4 P1：工单、风控、通知的业务闭环还不完整

当前已有工单状态机、证据索引、风控命中处置和审计补偿，但审查设计中的处罚服务、统一审计服务、通知链路并未完全落地。

整改方向：

- 先补“风控命中 -> 工单 -> 处理结果 -> 审计”的可追踪链路；
- 明确处罚动作是否属于当前模块职责；
- 对通知失败补偿进行真实联调；
- 暂不直接拆 `workordersvc`、`punishsvc`、`auditsvc`。

### 4.5 P1：前端业务页面复用过度

多个后台菜单复用 `console/index.vue`，虽然降低了开发成本，但订单详情、工单处置、统计分析等复杂场景的交互深度有限。

整改方向：

- 先按用户真实操作路径补足订单详情和工单详情；
- 统计页补充明确的指标更新时间、筛选限制和错误展示；
- 只有当页面复杂度继续增长时，再按领域拆分 Vue 页面。

## 五、暂不建议立即执行的工作

以下工作可以作为架构演进方向，但不应直接列为当前 P0 整改：

1. 一次性创建 `couponsvc`、`workordersvc`、`punishsvc`、`reportsvc`、`auditsvc` 五个服务；
2. 在没有明确数据所有权前拆分现有运营表；
3. 为满足设计文档形式而增加空壳 RPC；
4. 在未完成联调前重写现有 adminsvc；
5. 未经确认直接执行共享数据库迁移；
6. 为了“看起来有大屏”而接入没有真实数据来源的 mock 指标。

## 六、整改任务建议

### 阶段一：P0 收口

1. 统一导出类型的前后端契约；
2. 更新历史测试报告和接口总览；
3. 复测当前已开放路由；
4. 核对两份管理后台迁移脚本是否已在目标环境执行；
5. 验证订单取消、退款、改派、导出下载和审计补偿。

### 阶段二：P1 能力补强

1. 统一统计指标口径并补充边界测试；
2. 完善风控命中到工单的追踪信息；
3. 验证通知失败后的 outbox/job 补偿；
4. 补足订单轨迹、工单详情和统计页面的真实操作体验；
5. 评估同步发券的容量上限和异步化时机。

### 阶段三：P2 架构演进

在阶段一和阶段二完成后，根据实际瓶颈评估拆分顺序：

1. `reportsvc`
2. `workordersvc`
3. `couponsvc`
4. `auditsvc`
5. `punishsvc`

拆分前必须补充：服务职责、数据所有权、proto、事件、失败补偿、部署方式和回滚方案。

## 七、当前未决问题

1. 部门审查要求的是“按设计文档补齐服务”，还是“证明当前后台可交付并修复真实问题”？
2. 近期验收是否必须包含地图大屏、实时运力监控和完整财务报表？
3. 目标测试环境中 `07_admin_operation_business.sql` 和 `09_admin_export_audit_task.sql` 是否已经执行？
4. 当前模块三是否允许协调模块四、模块五、模块六共同完成跨服务联调？
5. 导出功能近期验收标准是只支持订单，还是必须支持用户、司机、日志和统计四类数据？

## 八、当前建议结论

当前模块三适合的目标不是追求“设计中的 14 个服务全部出现”，而是：

> 先把已有 adminsvc 能力收口成可验证、可追踪、前后端一致的后台系统，再根据真实性能和领域复杂度逐步拆分服务。
