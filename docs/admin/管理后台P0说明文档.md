# 管理后台 P0 说明文档

> 适用范围：`api/admin`
>
> 目标：先完成管理后台最小可用闭环，覆盖登录鉴权、操作日志、用户列表/详情、司机审核、订单列表/详情。
>
> 当前说明：本文前半部分保留 P0 初始建设目标；第 12 节记录截至 2026-08-20 当前后台管理模块已经落地的真实功能范围。

## 1. 目标与边界

### 1.1 P0 目标

P0 阶段只做管理后台最核心的只读管理能力和少量审核动作，确保后台可以先跑起来、先能看、先能审。

本阶段包含：
- 管理员登录、注册、退出、当前账号信息
- 操作日志查询
- 用户列表、用户详情
- 司机审核列表、审核详情、通过、驳回
- 订单列表、订单详情

### 1.2 暂不包含

以下内容留给后续版本：
- 优惠券模板配置
- 营销活动配置
- 数据统计报表
- 后台冻结/拉黑/取消订单等高风险操作
- 独立 RPC 服务拆分

## 3. 总体架构

早期 P0 草案曾采用“网关直连数据库”的方式；当前代码已经统一调整为 `api/admin -> rpc/adminsvc`：

```text
HTTP Router -> Logic Adapter -> rpc/adminsvc -> MySQL / Redis / 下游 RPC
```

### 3.1 分层职责

- `handler`：接收 HTTP 请求、解析参数、返回统一响应
- `logic`：只做 HTTP 到 adminsvc protobuf 的参数转换、token 透传和响应映射
- `rpc/adminsvc`：承载业务规则、权限判断、状态转换、数据库读写和下游 RPC 调用
- `model`：承载 HTTP 层会话 DTO 等少量模型
- `types`：承载请求/响应 DTO
- `svc`：集中初始化 MySQL 连接和 adminsvc RPC 客户端；HTTP 层不再初始化本地业务仓储

### 3.2 设计原则

- 所有后台接口统一走 Bearer Token
- 所有敏感操作必须写操作日志
- 分页列表统一限制最大 `page_size=100`
- 后台尽量只做管理和审核，不直接改动乘客业务主流程

## 4. P0 功能说明

### 4.1 登录鉴权

#### 功能

- 管理员注册
- 管理员登录
- 管理员退出
- 获取当前登录管理员信息
- 获取当前角色菜单

#### 数据流

```text
前端登录页 -> /admin/v1/auth/login
  -> api/admin 解析账号密码
  -> adminsvc.Login
  -> adminsvc 查询 admin_user、bcrypt 校验密码
  -> adminsvc 写 Redis 会话 token
  -> 返回 token 和管理员信息
```

```text
前端请求业务接口
  -> Authorization: Bearer <token>
  -> api/admin 调用 adminsvc.ValidateSession 校验会话
  -> 进入业务逻辑
```

#### 关键规则

- 首个管理员可免登录注册
- 后续注册必须由超管账号发起
- 密码使用 bcrypt 存储
- token 存 Redis，退出时删除
- session 过期时间由配置控制

### 4.2 操作日志

#### 功能

查询后台关键动作记录，便于审计和排障。

#### 典型记录场景

- 管理员注册
- 管理员登录
- 司机审核通过
- 司机审核驳回
- 后续新增的高风险后台操作

#### 数据流

```text
后台操作 -> adminsvc 写入 admin_operation_log
           -> 前端通过列表接口查询
```

#### 字段说明

- `admin_id`：操作管理员
- `module`：模块名，如 `auth`、`driver`、`order`
- `action`：动作名，如 `login`、`approve`
- `target_type`：目标类型
- `target_id`：目标主键
- `detail`：补充说明
- `ip`：来源 IP

### 4.3 用户列表 / 详情

#### 功能

- 查看乘客用户列表
- 查看单个用户详情

#### 数据来源

- 主表：`user`
- 软删除过滤：`deleted_at IS NULL`

#### 数据流

```text
前端用户列表页
  -> 传分页和筛选条件
  -> api/admin 转发 adminsvc.ListUsers
  -> adminsvc 查询 user 表
  -> 返回列表 DTO
```

```text
前端用户详情页
  -> api/admin 转发 adminsvc.GetUser
  -> adminsvc 根据 user ID 查询
  -> 返回用户基础资料
```

#### 筛选建议

- 关键词：手机号、昵称、实名
- 状态：正常 / 冻结 / 注销
- 注册时间范围

### 4.4 司机审核

#### 功能

- 司机认证审核列表
- 司机认证详情
- 审核通过
- 审核驳回

#### 数据来源

- `driver_certification`
- `driver`
- `driver_vehicle`
- 审核动作写入 `admin_operation_log`

#### 数据流

```text
审核列表
  -> api/admin 转发 adminsvc.ListDriverCertifications
  -> adminsvc 联查 driver_certification + driver + driver_vehicle
  -> 返回审核摘要
```

```text
审核通过
  -> api/admin 转发 adminsvc.ApproveDriverCertification
  -> adminsvc 调用 driversvc.ApproveCertification
  -> driversvc 事务更新 certification、driver、driver_vehicle
  -> adminsvc 写操作日志；失败时写 admin_audit_outbox 补偿记录
```

```text
审核驳回
  -> 更新 certification 审核结果
  -> 保留司机待审核状态
  -> 写操作日志
```

#### 关键约束

- 通过和驳回都要记录审核人、审核时间、审核备注
- 审核通过必须事务化，避免状态不一致
- 审核通过后司机和车辆状态同步变为可用

### 4.5 订单列表 / 详情

#### 功能

- 查询订单列表
- 查询订单详情

#### 数据来源

- `ride_order`
- `order_status_log`
- `dispatch_record`
- `order_price`
- `payment`
- `settlement`

#### 数据流

```text
订单列表
  -> api/admin 转发 adminsvc.ListOrders
  -> adminsvc 查询 ride_order
  -> 返回基础订单信息
```

```text
订单详情
  -> api/admin 转发 adminsvc.GetOrder
  -> adminsvc 查询 ride_order 主表
  -> 追加状态流转、派单、价格、支付、结算信息
  -> 组合成详情页 DTO
```

#### 关键说明

- 订单详情是聚合查询，不改订单状态
- 后台只读展示为主，后续再扩展取消等操作

## 6. 接口规范

### 6.1 通用请求头

```text
Authorization: Bearer <token>
Content-Type: application/json
```

### 6.2 通用分页参数

- `page`：默认 `1`
- `page_size`：默认 `20`，最大 `100`

### 6.3 通用响应格式

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

### 6.4 常见错误码

- `40001`：请求参数错误
- `40003`：无权限
- `40004`：未登录或 token 无效
- `40401`：资源不存在
- `40902`：资源冲突
- `50000`：系统错误

## 8. 实现细节

### 8.1 会话

- Redis 保存管理员会话
- token 作为 Redis key 后缀
- 会话内容至少包含管理员 ID、用户名、角色

### 8.2 审核事务

司机审核通过时必须保证：

1. 审核记录更新成功
2. 司机状态更新成功
3. 车辆状态更新成功
4. 事务提交成功

任何一步失败都必须回滚。

### 8.3 详情聚合

订单详情页面建议一次返回以下信息：

- 订单主信息
- 状态流转日志
- 派单记录
- 价格明细
- 支付信息
- 结算信息

这样前端无需多次请求即可完成详情页渲染。

## 9. 前后端交互规范

### 9.1 前端

- 列表页使用分页 + 筛选
- 详情页单独拉取详情接口
- 审核动作必须弹二次确认
- 所有列表页都应支持空状态展示

### 9.2 移动端

P0 阶段管理后台不直接面向移动端，但后台审核和订单查询依赖的业务数据来自乘客端、司机端和订单服务。

### 9.3 后续联调原则

- 后台不直接篡改乘客端下单逻辑
- 司机审核、订单详情应尽量从统一业务表读数据
- 后续若拆分 RPC，再把仓储查询切换为服务调用

## 10. 技术难点

### 10.1 难点一：事务一致性

司机审核会同时更新多张表，必须保证状态一致。

### 10.2 难点二：订单详情聚合

订单详情涉及多张表，字段映射和空值处理要统一，否则前端容易拿到不完整数据。

### 10.3 难点三：鉴权与会话失效

Redis 会话过期、退出登出、非法 token 都要统一处理，避免后台误放行。

### 10.4 难点四：迁移顺序

后台依赖的业务表必须先于接口验证创建，否则列表和详情会返回系统错误。

## 12. 当前后台管理已实现功能

> 本节以当前 `api/admin` 路由、`rpc/adminsvc` proto、adminsvc logic 和本地联调结果为准，区分“已实现可调用”和“仍需后续完善”的能力。

### 12.1 总体架构现状

当前后台管理模块已经从早期“HTTP 直连数据库”演进为以下边界：

```text
前端 / Postman
  -> api/admin HTTP 网关
  -> 调用 adminsvc 校验管理员会话
  -> 参数转换为 adminsvc protobuf 请求
  -> rpc/adminsvc 执行业务逻辑
  -> 必要时同步调用 ordersvc / driversvc
  -> MySQL 查询或更新真实业务表
```

各层职责如下：

| 层级 | 当前职责 |
| --- | --- |
| `api/admin` | HTTP 路由、登录态鉴权、Path/Query/Body 参数解析、统一 JSON 响应、错误码映射 |
| `rpc/adminsvc` | 后台核心业务 RPC，包括用户、司机审核、订单、优惠券、活动、统计、导出、风控、日志 |
| `rpc/ordersvc` | 后台取消订单时由 `adminsvc` 同步调用 `ordersvc.CancelOrder` |
| `rpc/driversvc` | 司机认证审核通过/驳回时由 `adminsvc` 同步调用 `driversvc` |
| MySQL | 保存后台用户、操作日志、订单、司机、优惠券、活动、风控等真实表数据 |
| Redis | 保存后台管理员登录会话 token |
| `rpc/pricesvc` | 计价规则列表、详情、新增、编辑、启停由 `adminsvc` 转发到 `pricesvc`，后台不直接修改 `price_rule` |
