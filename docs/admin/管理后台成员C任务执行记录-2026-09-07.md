- 管理员登录验证：`POST /admin/v1/auth/login`（admin/123456）返回超管 token，接口层可用。

### 1.2 八个下游 NonBlock 确认
- `rpc/adminsvc/etc/admin.yaml` 与一键脚本模板：Orders/Users/Dispatch/Drivers/Locations/Prices/Pays/Push 共 **8 个下游全部 `NonBlock: true`**（懒连接，下游未起不影响 adminsvc 启动）。
- `rpc/adminsvc/internal/svc/servicecontext.go`：集中装配 8 个下游 `zrpc.NewClient`，并提供 `DisableDownstreamRPC` 开关支持最小本地模式；未配置的端点回退到本机默认端口。
- 实证：本地 pushesvc(9002) 未运行，adminsvc 仍正常启动运行——体现 NonBlock 特性。

### 1.3 订单详情聚合与降级联调（真实数据）
- `GET /admin/v1/orders?page=1&page_size=3`：正常返回（走 `adminsvc.ListOrders -> ordersvc.ListOrders`），共 52 单。
- `GET /admin/v1/orders/64`：主信息（ordersvc）、`status_logs`（ordersvc.ListOrderStatusLogs）、`dispatch_records`（dispatchsvc）正常聚合；`price/payment/settlement` 因该订单无对应记录返回空并标记 `degraded:["price","payment","settlement"]`。
- 实现佐证（`getorderlogic.go`）：对 status_logs/dispatch_records/price/payment/settlement 各自独立 try/catch，失败追加 `degraded` 标识，主链路不因任一子块失败而中断——满足“可串起（降级）、不阻塞主流程”。
- 结论：P0 主链路可观测性（订单只读聚合 + 降级标识）验证通过；退款/改派为写操作，属强一致路径（改数据需用测试单，未在本轮对真实订单执行，避免污染业务数据）。

## 二、P1：审计 outbox job 重放消费方（实现已齐备，本轮运行验证并修复启动阻碍）

### 2.1 现状核对
`job/internal/task/admin_audit_outbox.go` 已实现完整重放消费逻辑：

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 轮询 | `RetryAdminAuditOutbox` 每 30 秒 | 取 `retry_count < maxRetry` 且 `pending` 或超时 `running` 记录，单轮上限 50 |
| 抢占 | `id + status IN (pending,running)` 条件更新 running | 防多实例重复处理 |
| 审计重放 | `replayOperationLog` | 重写 `admin_operation_log` |
| 司机冻结重放 | `replayDriverFreeze -> driversvc.FreezeDriver` | job 不直改司机表 |
| 通知重放 | `_notice/_push/_notify` → `pushsvc.SendNotice/SendPush` | 失败回表补偿 |
| 失败重试与最大上限 | `markAdminOutboxFailed` | 未超限回 `pending`，超过 `AdminOutboxMaxRetry`(默认 5) 置 `failed` 并留 `failure_reason` |
| 死信语义 | `failed` 状态保留 | 作为人工处理窗口，可在管理后台 `/admin/v1/notification-outbox` 查询 |

### 2.2 本地运行验证与修复
- 构建 `job.exe` 并在本机以 `job/etc/job.yaml` 试跑：进程可稳定运行，预检输出 `refund=0 dispatch=0 outbox_pending=0 outbox_failed=0`，`RetryAdminAuditOutbox` 每 30 秒扫描成功（“管理后台 outbox 扫描完成: 拉取 0 条 成功 0 条”）。
- 过程中修复三类启动阻碍（配置与代码对齐）：
  1. `job/etc/job.yaml`：补 `kafka.brokers` 段（config 声明 KafkaConf 但 yaml 缺失导致启动报错）；`driverrpc.target` 5055 → **50055**；orderrpc/dispatchrpc/driverrpc/pushrpc 全部补 `NonBlock: true`（否则 pushesvc 未运行时 `zrpc.MustNewClient` 阻塞拨号 panic）。
  2. `job/internal/svc/servicecontext.go`：driversvc fallback 硬编码端口 `5055` → `50055`。
  3. `job/internal/task/compensation_dry_run.go`：`MIN(created_at)` 对空表返回 NULL 扫描 `*time.Time` 报错，改用 `sql.NullTime` 处理。
- `go build ./job` 与 `go vet ./job/...` 通过。

### 3.2 人群包/灰度发券：现状与设计建议（代码待办）
现状（`rpc/adminsvc/internal/logic/adminservice/admin_extension_logic.go` `IssueCoupon`）：
- `target_type` 接受 `user/batch/crowd`，但三者都要求 `target_config.user_ids` 非空——**未真正实现人群/灰度选择**，等价“显式用户发放”。
- 服务端校验由 `usersvc.AdminIssueCoupon` 完成（券库存/上限/有效期）；adminsvc 本地事务写 `admin_coupon_issue_task` + `admin_coupon_publish_record` + 审计。
- 前端仅 `web/admin` 发券入口按显式用户提交。

建议实现路径（需 usersvc 配合，未在本轮实施以免跨服务欠设计）：
1. usersvc 提供“后台可选人群查询”RPC（如按 `city_code / register_source / status / 最近下单时间` 返回符合条件的 `user_id` 分页），口径需先定：当前 `user` 表无权威 `city_code`，城市维度需以最近订单 `city_code`（`10_order_city_code.sql`）推导或先支持确定性人群字段。
2. adminsvc `IssueCoupon` 对 `crowd`：先调人群查询 RPC 得到候选 user_ids（限量截断），再走现有 `usersvc.AdminIssueCoupon` 发放；`batch` 保留为后续分片批次。
3. 灰度语义：`publish_scope=gray` 与 `target_config.city_codes` 用于活动发布；发券灰度可叠加 `percent` 抽样，需在 `admin_coupon_issue_task` 记录抽样配置便于对账。
4. 前端 `punishments`/发券弹窗对 `crowd` 展示人群摘要（预估人数）而非用户列表。
